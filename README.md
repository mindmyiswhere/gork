# gork

Распределённый таск-оркестратор на Go с gRPC и Redis.

## Что это

`gork` — минималистичная система для распределённого выполнения задач. Клиент отправляет задачу, оркестратор ставит её в приоритетную очередь, воркеры забирают задачи и выполняют их. Состояние каждой задачи видно в реальном времени.

## Возможности

- **gRPC API** — типобезопасный контракт через protobuf
- **Bidi-стриминг** между воркером и оркестратором: задачи, heartbeat, результаты в одном соединении
- **Server-streaming** для клиента: watch статуса задачи в реальном времени
- **Приоритетная очередь** на Redis Sorted Set
- **Retry-политика** с настраиваемым `maxRetries`
- **Reaper** — автоматически возвращает в очередь задачи, чьи воркеры упали
- **Lease-based** отслеживание аренды задач
- **Отмена задач** — как в очереди (`PENDING`), так и выполняющихся (`RUNNING`) с прерыванием через стрим
- **Graceful shutdown** всех компонентов

## Запуск

```bash
# 1. Поднять Redis

# 2. Создать .env из шаблона
cp .env.example .env

# 3. Запустить оркестратор (в отдельном терминале)
make run-orch

# 4. Запустить воркер (в отдельном терминале)
make run-worker
```

## Использование

### Отправить задачу

```bash
PAYLOAD=$(echo -n '{"to":"a@b.com","subject":"hi","body":"hello"}' | base64)
grpcurl -plaintext -d "{
  \"type\": \"send_email\",
  \"payload\": \"$PAYLOAD\",
  \"priority\": 10,
  \"maxRetries\": 3
}" localhost:50051 orchestrator.v1.ClientService/SubmitTask
```

### Получить статус

```bash
grpcurl -plaintext -emit-defaults \
  -d '{"taskId":"<id>"}' \
  localhost:50051 orchestrator.v1.ClientService/GetTask
```

### Следить за задачей в реальном времени

```bash
grpcurl -plaintext \
  -d '{"taskId":"<id>"}' \
  localhost:50051 orchestrator.v1.ClientService/WatchTask
```

Выводятся все переходы статуса: `PENDING → RUNNING → SUCCEEDED`.

### Отменить задачу

```bash
grpcurl -plaintext \
  -d '{"taskId":"<id>"}' \
  localhost:50051 orchestrator.v1.ClientService/CancelTask
```

## Встроенные типы задач

| Тип | Что делает | Длительность |
|-----|-----------|--------------|
| `send_email` | Эмулирует отправку письма | 2 с |
| `resize_image` | Эмулирует ресайз картинки, падает в 30% случаев | 5 с |
| `generate_report` | Эмулирует генерацию отчёта | 8 с |

Обработчики зарегистрированы в `cmd/worker/main.go`. Чтобы добавить свой — реализуй функцию `Handler` и зарегистрируй в `HandlerRegistry`.

## Как это работает

### Поток задачи

1. Клиент вызывает `SubmitTask` — оркестратор создаёт задачу в Redis и кладёт в приоритетную очередь (`ZADD tasks:queue`).
2. Воркер держит открытый bidi-стрим с оркестратором. Оркестратор вытаскивает задачу из очереди через **Lua-скрипт** (атомарно: `ZREM` + `HSET status=RUNNING` + `ZADD leases`) и отправляет её воркеру через `TaskAssignment`.
3. Воркер выполняет задачу в отдельной горутине и шлёт обратно `TaskResult` через тот же стрим.
4. Оркестратор обрабатывает результат: при успехе — финализирует, при провале — увеличивает `attempt` и возвращает в очередь (если попытки остались).
5. `WatchTask` подписывается на Redis pub/sub и стримит клиенту все переходы статуса.

### Устойчивость к падениям

Когда воркер берёт задачу, в Redis пишется **lease** — дедлайн, до которого задача считается «в работе». Пока воркер жив, он продлевает lease на каждом heartbeat. Если воркер упал — lease истекает, и **reaper** через 2 секунды находит задачу. Дальше:

- если попытки остались — возвращает в очередь с `attempt++`,
- если попытки кончились — финализирует `FAILED`.

### Отмена

- **`PENDING`** — оркестратор убирает из очереди и сразу переводит в `CANCELLED`.
- **`RUNNING`** — оркестратор ставит флаг в Redis. Отдельная горутина раз в 2 секунды проверяет флаги и отправляет воркеру `CancelCommand` через тот же стрим. Воркер прерывает контекст задачи, обработчик корректно завершается. Оркестратор финализирует `CANCELLED`.
